# Architecture & research notes

## Pipeline
```
 idea + director's notes
        │  (Claude Code session, your subscription — CLAUDE.md, /develop-story, /revise)
        ▼
 episodes/<id>/episode.json ──► validate (schema + feasibility: every action/target/camera/sound/style checked)
        │
        ▼  engine/src/compiler
 TTS pre-pass (Kokoro, local) ─► compile scenes: markers → timelines, locomotion planning, crowd behaviours,
                                 prop trajectories, physics bakes (Rapier, seeded) ─► compile videos: shots → edit,
                                 scene events → audio cues, captions, HUD, score
        │
        ▼  engine/src/runtime  (browser bundle, Three.js)          engine/src/render
 frame(t) is a pure function of time ──► headless Chromium ──► JPEG frames ──► FFmpeg H.264
        │
        ▼  engine/src/audio                        engine/src/covers        engine/src/qc
 voices + SFX + music + ambience mix, ducking,     3 covers, 1 source       ffprobe/ffmpeg checks,
 EBU R128 loudness ─► mux                          frame                    contact sheets
        ▼
 productions/<id>/final/*.mp4, covers/, qc/, report.json, produce.log
```

## Why Three.js in headless Chromium, not Godot or Blender, as the primary renderer
Chosen after inspecting the environment and weighing the options in the brief:
- **One language end to end.** The compiler, renderer and (Phase 3) website are TypeScript. The same runtime
  that renders final frames can run *live* in the website as an interactive shot preview: scrub any shot
  instantly before rendering.
- **Deterministic offline capture.** Every frame is computed from time alone. Frames can be rendered in any order,
  in parallel, or re-rendered selectively.
- **Runs everywhere for free.** It uses the GPU on Windows (ANGLE/D3D11) and falls back to software in containers.
  In this environment Godot 4 and Blender binaries could not be downloaded (blocked hosts), so they could not have
  been verified here anyway.
- **Blender stays in the toolchain** as the asset-preparation tool (rig/clean/export glTF). The engine already
  imports rigged glTF characters with their animation clips (the CC0 robot referee).
- **Remotion was not needed.** Editing (cuts, ramps, overlays, captions) happens in the same render pass, and
  audio/encode goes through FFmpeg. That avoids a second pipeline. If a template-driven motion-graphics layer is
  wanted later, Remotion (free for individuals) can consume the same compiled JSON.

## Key design decisions
- **Scene vs shot.** Choreography (scene) is separate from the edit (shots), so camera and editing feedback never
  require re-animating.
- **Markers, not timestamps.** Story beats are named; shots and other tracks reference them, so changing one line's
  length doesn't break the edit.
- **Feasibility before rendering.** Unknown actions, targets, sets, cameras, sounds and styles are errors with a fix
  hint. Nothing is silently dropped.
- **Simulated vs scripted.** Physics bakes are flagged `simulated: true` in the compiled data. Scripted arcs are
  guaranteed outcomes.
- **Reproducible.** Seeds everywhere (crowd variation, stagger, physics jitter). The same spec gives the same video.
- **Safe parallel work.** Each process bundles its own runtime file, so preview renders can't disturb a running production.
